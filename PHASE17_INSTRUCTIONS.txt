PHASE 17 — GLOBAL NAVIGATION CMS (INCREMENTAL / SAFE)

Goal
----
Add a database-backed navigation layer for public header/footer menus without changing
existing public HTML, CSS, JavaScript, navigation labels, or ordering automatically.

Important
---------
This package intentionally does NOT overwrite includes/header.php, footer.php,
head.php, or footerLink.php because the exact template source was not included in the
uploaded project files. It also does not seed navigation rows. Your current public menu
therefore remains unchanged after this phase is installed.

Install
-------
1. Import:
   database/phase17_navigation.sql

2. Copy:
   app/core/Navigation.php
   app/core/NavigationManager.php
   into the matching project paths.

3. In publicV6/app/bootstrap.php, add ONE require_once with the other core files:
   require_once __DIR__ . '/core/Navigation.php';
   require_once __DIR__ . '/core/NavigationManager.php';

4. Add the admin folder:
   scadmin/navigation/

5. Add the new permission `manage_navigation` to the Admin role / user as appropriate.
   The SQL only creates the permission record; it does not grant it to an editor.

Admin usage
-----------
Open:
   /scadmin/navigation/

The screen supports separate Header and Footer navigation locations, parent items,
ordering, visibility, target, and optional icon class.

Public integration
------------------
Do NOT replace your current public menu yet unless the exact current template source
has been checked. Once includes/header.php and footerLink.php are available, the menu
loops can be changed to use:

   Navigation::all('header')
   Navigation::all('footer')

The returned array is hierarchical and contains:
   id, parent_id, label, url, target, icon_class, sort_order, is_active, children

Recommended integration rule:
- Preserve all current wrapper elements/classes and CSS hooks.
- Replace only the hard-coded menu data/loop.
- Do not change visible labels or ordering during the first migration.
- Seed the DB from the exact current menu only after comparing the real template source.

Security
--------
- All admin pages use the existing Auth/CSRF/session stack.
- Toggle/delete actions are POST-only and require a CSRF token.
- URLs reject whitespace and javascript: URLs.
- Child items cannot be assigned to a parent in another location.
- Deleting a parent with children is blocked.
- AuditLogger is used when available.
- No public authentication is introduced.

Rollback
--------
Because this phase is additive, rolling back the public integration only requires
removing the two Navigation require lines and leaving the existing templates unchanged.
The table/permission may remain harmlessly unused, or be removed manually after a backup.
